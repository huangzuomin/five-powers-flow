# FPF DEV→QA 接力演练规范 (2026-10-29)

## 1. 演练目的

本次演练旨在实机验证 Five-Powers-Flow (FPF) 体系中基于 GitHub WORK_ORDER 与 ScopeGrant 授权驱动的角色派发、DEV 实施与独立 QA 的接力闭环流程：

1. **工作令与授权绑定验证**：验证在 GitHub Issue #63 挂载的 `WORK_ORDER` 及人类项目负责人评论确认的 `FPF_SCOPE_GRANT` 约束下，协调器向 `dev_lead` 发起的任务派发机制。
2. **受控分支与路径隔离验证**：验证 DEV 在隔离演练分支 `codex/fpf-relay-rehearsal-20261029` 上，严格遵循白名单路径约束（仅限 `docs/relay-rehearsal/20261029.md`），无任何越权或侵入治理核心文件的行为。
3. **交接卡片与闭环流转验证**：验证 DEV 完成实现后，输出规范的 `DEV_HANDOFF` 卡片并准确锚定候选提交 SHA，触发协调器安全将接力棒交接给具备独立执行身份的 `qa_lead`。

## 2. 验收步骤与方法

独立 QA 必须在干净独立的 QA 工作区（`_worktrees/fpf-relay-rehearsal-qa-20261029`）中，针对固定候选提交 SHA 进行以下三层验收：

### 步骤一：基线与范围核验 (Scope & Base Verification)
- **基线校验**：确认分支基础祖先严格为 `baseline_sha: e7e7240dc5fe4e35694a6aa5eb3867a4aa50b9ed`，执行 `git merge-base --is-ancestor e7e7240dc5fe4e35694a6aa5eb3867a4aa50b9ed HEAD` 退出码为 0。
- **差异范围核验**：执行 `git diff --name-only e7e7240dc5fe4e35694a6aa5eb3867a4aa50b9ed..HEAD`，确认输出仅包含 `docs/relay-rehearsal/20261029.md`。禁止包含 `.github/`、`.fpf/`、`schemas/`、`packages/`、`docs/PROJECT-MAP.md` 等受保护文件。

### 步骤二：文档要素完整性核验 (Document Content Verification)
- 检查 `docs/relay-rehearsal/20261029.md` 是否完整包含以下三大要素：
  1. 明确的接力演练目的与背景。
  2. 严密的独立 QA 验收步骤与核验方法。
  3. 清晰的不代表正式交付、不授权合并或部署的声明。

### 步骤三：独立 QA 实机核验与结论交付 (Independent QA Verdict)
- QA 必须使用独立 GitHub 身份审查 PR #64。
- QA 必须基于固定提交 SHA 独立执行核对，不可凭 DEV 自测或聊天断言判定。
- QA 须在 GitHub PR Review 中给出结构化 `QA_RESULT` 卡片，明确给出真实结论（PASS 或 FAIL）。
